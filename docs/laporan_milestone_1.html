1. DESKRIPSI APLIKASI & ANALISIS PERMASALAHAN

Kawasan di sekitar kampus Universitas Gadjah Mada (UGM)—seperti Pogung, Karangmalang, Sekip, Blimbingsari, hingga Jalan Kaliurang—merupakan salah satu pusat pemukiman mahasiswa terpadat di Daerah Istimewa Yogyakarta. Setiap tahun ajaran baru, ribuan mahasiswa baru maupun mahasiswa lama berupaya mencari hunian kos yang dekat dengan fakultas mereka. Kendati demikian, proses penyebaran informasi kos-kosan selama ini masih bersifat terfragmentasi, tidak terstruktur, dan konvensional: tersebar melalui obrolan grup WhatsApp, spanduk yang terpasang di tiang listrik dan gang sempit, atau melalui jasa perantara (calo).

Kondisi konvensional tersebut menimbulkan tiga persoalan mendasar:

  1. Ketidakpastian Ketersediaan Kamar Riil: Pencari kos sering kali mendatangi lokasi kos secara fisik hanya untuk menemukan bahwa seluruh kamar telah terisi penuh. Tidak adanya indikator ketersediaan kamar yang diperbarui secara langsung (real-time) mengakibatkan inefisiensi waktu dan tenaga yang signifikan.
  2. Beban Operasional Pemilik Kos: Di sisi lain, pemilik kos kerepotan mempromosikan propertinya dan terus-menerus menerima pesan atau panggilan telepon menanyakan ketersediaan kamar, bahkan ketika seluruh unit kamarnya sudah terisi penuh.
  3. Ketiadaan Kurasi dan Risiko Informasi Fiktif: Tanpa adanya mekanisme verifikasi terpusat, pencari kos rentan terhadap fasilitas fiktif, ketidakjelasan peraturan kos, perbedaan harga sewa yang tidak transparan, hingga potensi penipuan uang muka sewa kamar.

Untuk menjawab persoalan tersebut, aplikasi Singgah-sana dibangun sebagai sistem backend RESTful API berbasis Node.js (Express.js) dan basis data MongoDB yang mengadopsi mekanisme direktori terkurasi mirip platform pencarian kos nasional (seperti Mamikos). Sistem ini menengahi pemilik kos dan pencari kos melalui mekanisme kurasi ketat:

  • Pemilik kos mendaftarkan data properti lengkap dengan foto, titik koordinat peta (latitude/longitude), fasilitas, harga bulanan, dan kuota kamar.
  • Administrator memverifikasi keabsahan data kos sebelum ditampilkan ke publik melalui alur persetujuan (approval workflow). Kos baru secara otomatis berstatus pending dan tidak dapat diakses publik hingga disetujui oleh Administrator.
  • Pencari kos dapat melakukan pencarian berbasis kata kunci dan filter multi-dimensi (tipe kos putra/putri/campur, rentang tarif sewa, fasilitas unggulan, dan hanya menampilkan kos yang memiliki sisa kamar kosong), menandai kos favorit, serta mengirim pesan pertanyaan langsung kepada pemilik kos.

2. ANALISIS KEBUTUHAN PENGGUNA (USER STORIES)

Berdasarkan analisis kebutuhan pemangku kepentingan (stakeholders) pada skenario kasus US2 — Portal kos-kosan, wewenang sistem diklasifikasikan ke dalam tiga peran pengguna (Role-Based Access Control):

A. Pencari Kos (Mahasiswa & Masyarakat Umum)

  • US-P01: Sebagai Pencari, saya ingin mendaftar akun dan login ke dalam sistem agar mendapatkan token otentikasi (JWT) untuk mengakses fitur personalisasi.
  • US-P02: Sebagai Pencari, saya ingin melihat direktori kos yang telah diverifikasi (status approved) lengkap dengan foto, tarif bulanan, tipe kos, dan alamat lengkap.
  • US-P03: Sebagai Pencari, saya ingin menyaring daftar kos berdasarkan tipe kos (putra, putri, campur), batas harga sewa minimum dan maksimum, fasilitas khusus (AC, WiFi, kamar mandi dalam, parkir), serta menyaring kos yang benar-benar masih memiliki kamar kosong (kamar_tersedia > 0).
  • US-P04: Sebagai Pencari, saya ingin melihat detail spesifik suatu kos, meliputi titik koordinat geografis untuk pemetaan, fasilitas lengkap, luas kamar, dan peraturan kos.
  • US-P05: Sebagai Pencari, saya ingin menandai (bookmark) kos ke dalam daftar favorit saya agar dapat dibuka kembali dengan cepat tanpa perlu mencari ulang.
  • US-P06: Sebagai Pencari, saya ingin mengirimkan pesan pertanyaan (inquiry) langsung kepada pemilik kos mengenai survei lokasi atau konfirmasi ketersediaan kamar.

B. Pemilik Kos (Mitra Penyedia Kamar)

  • US-O01: Sebagai Pemilik, saya ingin mendaftarkan kos baru dengan mengisi data nama, deskripsi, alamat, titik koordinat, fasilitas, harga sewa bulanan, kuota total kamar, sisa kamar tersedia, dan foto properti, dengan status verifikasi awal otomatis pending.
  • US-O02: Sebagai Pemilik, saya ingin melihat daftar seluruh kos milik saya sendiri beserta status verifikasinya (pending, approved, atau rejected disertai catatan alasan penolakan).
  • US-O03: Sebagai Pemilik, saya ingin memperbarui informasi kos miliknya, terutama menyesuaikan jumlah ketersediaan kamar kosong saat terjadi sewa baru atau penghuni keluar, agar tidak dihubungi terus-menerus saat kamar penuh.
  • US-O04: Sebagai Pemilik, saya ingin melihat pesan pertanyaan yang masuk dari pencari kos dan memberikan balasan respon atas pertanyaan tersebut.
  • US-O05: Sebagai Pemilik, saya ingin menghapus data kos milik saya sendiri jika properti tersebut sudah tidak lagi disewakan.

C. Administrator (Pengelola Utama Portal)

  • US-A01: Sebagai Admin, saya ingin melihat antrean pendaftaran kos dari seluruh pemilik kos dengan penyaringan status (pending, approved, dan rejected).
  • US-A02: Sebagai Admin, saya ingin memverifikasi pendaftaran kos dengan mengubah status menjadi disetujui (approved) sehingga tampil di publik, atau menolak (rejected) disertai catatan verifikasi.
  • US-A03: Sebagai Admin, saya ingin melihat daftar seluruh pengguna sistem (Pencari, Pemilik, Admin) beserta informasi peran dan kontaknya.
  • US-A04: Sebagai Admin, saya ingin melihat dashboard agregasi statistik sistem, mencakup total kos terdaftar, jumlah kos pending verifikasi, kos approved, total kamar kosong tersedia, serta sebaran pengguna.
  • US-A05: Sebagai Admin, saya ingin mengunduh berkas rekapitulasi data kos dalam format CSV untuk keperluan pelaporan dan arsip pembukuan berkala pengelola.

3. ANALISIS FITUR SISTEM

Berikut adalah daftar modul dan fitur yang telah diimplementasikan pada server backend Singgah-sana sesuai dengan prinsip rekayasa perangkat lunak web dan materi PAW01 s.d. PAW06:

No Modul Fitur Deskripsi Implementasi Aktor Terkait
1 Autentikasi & Keamanan (BE4, BE5) Registrasi akun pengguna, login dengan enkripsi kata sandi menggunakan bcryptjs (10 salt rounds), penerbitan JSON Web Token (JWT) dengan masa berlaku 7 hari, dan middleware otorisasi Role-Based Access Control (RBAC) yang membatasi hak akses rute privat. Semua Role (Publik, Pencari, Pemilik, Admin)
2 Validasi Masukan Terpusat Middleware pemvalidasi format email, nomor telepon format Indonesia, batas minimal panjang kata sandi (min 6 karakter), format enum tipe kos, titik koordinat geografis, serta validasi kuota kamar tersedia tidak boleh melebihi kapasitas total. Sistem / Global
3 Manajemen Data Kos (CRUD) Operasi penambahan kos baru oleh pemilik, pembacaan detail kos, pembaruan fasilitas dan jumlah ketersediaan kamar, serta penghapusan data kos dengan validasi kepemilikan (ownership verification). Pemilik Kos, Admin
4 Alur Verifikasi Kos (Approval Workflow) Titik otorisasi kurasi: setiap kos baru yang diajukan pemilik berstatus pending dan secara ketat disaring agar tidak muncul di katalog publik. Administrator memverifikasi keabsahan data menjadi approved atau rejected disertai catatan audit verifikasi. Administrator
5 Direktori & Pencarian Multifilter Menampilkan seluruh kos berstatus approved dengan kemampuan filter simultan (pencarian nama/alamat, tipe putra/putri/campur, rentang harga sewa minimum dan maksimum, filter fasilitas khusus, serta opsi filter kamar tersedia > 0). Publik, Pencari Kos
6 Sistem Favorit (Bookmark) Pencari kos dapat menandai kos favorit ke dalam akun pribadinya. Sistem mengimplementasikan compound unique index (user_id + kos_id) pada MongoDB untuk mencegah duplikasi entri favorit. Pencari Kos
7 Sistem Pesan & Pertanyaan (Inquiry) Pencari kos dapat mengirim pertanyaan langsung ke pemilik kos tertentu; pemilik kos dapat memantau pesan masuk untuk propertinya dan memberikan tanggapan balasan secara terstruktur. Pencari Kos, Pemilik Kos
8 Pagination & Dynamic Sorting Dukungan parameter query ?page=&limit=&sort= (urutan harga terendah, harga tertinggi, dan data terbaru) guna menjamin skalabilitas dan efisiensi transfer data jaringan. Semua Role
9 Dashboard Agregasi Statistik Pemanfaatan MongoDB Aggregation Pipeline untuk menghitung metrik portal secara langsung: total kos aktif, pending verifikasi, rejected, total kamar tersedia, dan total pengguna per role. Administrator
10 Fitur Nilai Tambah (Nilai G6) 1. Pengelolaan berkas unggah foto kos menggunakan multer (limit 5MB).
2. Penyimpanan titik koordinat latitude/longitude untuk pemetaan peta (Leaflet / Google Maps).
3. Ekspor rekapitulasi data kos ke berkas CSV yang kompatibel dengan Microsoft Excel.		 Administrator, Pemilik

4. DAFTAR SPESIFIKASI RESTful API

Seluruh endpoint RESTful API dibangun dengan struktur yang konsisten menggunakan prefix Base URL pengembangan lokal (http://localhost:5000/api). Tabel di bawah ini merinci metode HTTP, rute endpoint, tingkat hak akses, dan deskripsi fungsionalitasnya:

Method Endpoint Hak Akses Deskripsi Fungsi
POST /api/auth/register Publik Pendaftaran akun baru (role: pencari atau pemilik)
POST /api/auth/login Publik Otentikasi kredensial pengguna dan penerbitan token JWT
GET /api/auth/me Private (All) Mengambil informasi profil akun yang sedang login
PUT /api/auth/profile Private (All) Memperbarui nama lengkap, nomor telepon, dan foto profil
GET /api/kos Publik Direktori kos berstatus approved (support multi-filter & paging)
GET /api/kos/:id Publik* Detail lengkap 1 kos (*jika pending hanya pemilik dan admin)
POST /api/kos Pemilik Mendaftarkan kos baru (status awal otomatis pending)
GET /api/kos/owner/my-kos Pemilik Melihat seluruh kos milik pemilik beserta status verifikasinya
PUT /api/kos/:id Pemilik, Admin Memperbarui data kos dan ketersediaan kamar kosong
DELETE /api/kos/:id Pemilik, Admin Menghapus data kos dari sistem
GET /api/admin/kos Admin Melihat seluruh kos terdaftar (pending, approved, rejected)
PATCH /api/admin/kos/:id/verifikasi Admin Verifikasi status kos (approved / rejected + catatan)
GET /api/admin/stats Admin Dashboard agregasi statistik portal kos dan ringkasan pengguna
GET /api/admin/users Admin Melihat daftar seluruh pengguna sistem beserta rolenya
GET /api/admin/export/kos Admin Mengunduh file CSV rekapitulasi data kos
GET /api/favorit Pencari Melihat daftar seluruh kos yang difavoritkan pencari
POST /api/favorit/:kosId Pencari Menambahkan kos tertentu ke daftar favorit pribadi
DELETE /api/favorit/:kosId Pencari Menghapus kos dari daftar favorit
POST /api/inquiries Pencari Mengirim pesan pertanyaan ke pemilik kos
GET /api/inquiries/my Pencari Melihat riwayat pertanyaan yang dikirim pencari
GET /api/inquiries/owner Pemilik Melihat daftar pesan pertanyaan masuk untuk kos miliknya
PATCH /api/inquiries/:id/reply Pemilik Membalas pesan pertanyaan dari pencari kos
